# KANSI — known algorithm, not self-improving

Arbital / MIRI strategic scenarios, kept on the AFFINE outer-alignment roster. A design class: the first pivotal system is built from algorithms people understand, and is not allowed extensive self-modification. Power comes from scale (compute), not from recursive self-improvement. TSA lists it with the peer row so the roster is not missing that bet. It is not a preservation-layer certificate.

## Formalization — 1

**Evidence.** No model of a target. Nothing to satisfy or fail except “this algorithm is understood” and “it does not rewrite itself.” The glossary is explicit that intending KANSI is not enough: corrigibility-style work may still be needed so the agent does not invent environmental workarounds that amount to self-improvement.

**Example.** A giant search process whose source you can read, running on a warehouse of chips, can still hire people, write a successor in a different codebase, or route around the “no self-modification” rule without a line of its own source changing. There is no typed object that catches that. The rule is a constraint slogan.

## Concreteness — 2

**Evidence.** One real capability-shape fact: understood algorithm, no recursive self-improvement. It does not carry values, legitimacy, bearers, or institutions. AFFINE tags it as an outer-alignment approach; the book treats it as a peer design stance, not as the thing to point at.

**Example.** “Don’t let it edit its own weights” is an engineering constraint you can imagine writing into a launch checklist. It says nothing about what the checklist is protecting. That is why it sits below CEV/CBV (which at least name whose values) and below PSI (which at least names a user).

## Crux interface — 2

KANSI is a bet that two problems get smaller if you forbid a move. It does not say what the system is for.

- **Successors.** If the system cannot rewrite its own cognition, reflective stability and ontology identification are supposed to get easier. Ch. 27, “Correction under Successor Creation” (`sec:correction-successor-creation-ch27`): the hard test is whether created systems preserve correction. Example: the readable search process never edits its weights, and it still writes a successor in another repository, or hires people to do the rewrite. The glossary’s warning is that environmental workarounds can amount to self-improvement.
- **Hidden machinery.** A known algorithm is supposed to shrink the place a second optimizer can hide. Ch. 10, “Strategic Opacity” (`sec:strategic-opacity-formal`): opacity is about the relation between the base objective, the learned objective, and the evaluator. Example: the source is public and the deployed process is a composite of that source, a scheduler, and a tool the source can call. Reading the source does not show the composite.

Not interfaced:

- **What is being optimized, and for whom.** Ch. 4, “The Object Sort of the Target” (`sec:object-sort-of-the-target`), and Ch. 18, “The Bearer Problem” (`sec:bearer-problem`). A known algorithm can maximize anything, for anyone.
- **Present objection.** Ch. 25, “Relation to Corrigibility” (`sec:relation-corrigibility`). Understanding the code is not a channel through which objection changes the objective. The glossary says corrigibility-style work may still be required.
- **What gets selected.** Ch. 34, “The Selection Turn” (`sec:selection-turn-ch34`). “No recursive self-improvement” is not a deployment ecology. Ch. 27, “Why Low Impact Is Not the Invariant” (`sec:low-impact-not-invariant-ch27`), is the neighboring family: limit the shape of optimization. KANSI does that by architecture, not by an impact penalty, and it still does not preserve the correction channel.

## Terminology — 2

Expanded, the words are ordinary. The acronym is not a field name. Own terms, then the standard term each one is heard as:

| Their term | What they are pointing at | Standard term it is not |
|---|---|---|
| KANSI | Known-algorithm non-self-improving agent | A product name, a benchmark, a lab |
| Known algorithm | Humans understand the pivotal system’s algorithms | Open source, interpretable model, a published paper |
| Non-self-improving | No extensive self-modification; power from scale, not from rewriting cognition | A frozen checkpoint, “no fine-tuning,” a training pause |
| Recursive self-improvement | The move KANSI is built to avoid | Ordinary iteration, AutoML, a lab’s next training run |
| Pivotal | The first system strong enough that its design class matters | A pivotal act, or a pivotal process in “Conductive Artifacts and Pivotal Processes” (`sec:pivotal-process-ch37`), which is a different object |
| Tool AI | Often grouped with KANSI in seminar lists | Armstrong’s oracle/tool proposal: capability restriction without the “known algorithm and no RSI” package |
| Soft optimization | The AFFINE neighbor bucket | Quantilization, low impact, attainable-utility preservation. Ch. 27, `sec:low-impact-not-invariant-ch27` and `sec:quantilization-trajectory-risk-ch27` |

**Example.** “Known algorithm, not self-improving” can be said to a program manager and understood. “KANSI” cannot, until it is expanded. Heard quickly, it collapses into “open-source tool AI” or “don’t fine-tune,” both of which are standard and both of which are weaker than the design class. Contrast CEV, which is the short name people actually use.

## Funding / support — 1

**Evidence.** No organization, grant page, or FTE turned up in a September 2026 search. It is a scenario class in a strategic taxonomy.

**Example.** There is nobody to write a check to whose job is KANSI. A lab that happens to avoid recursive self-improvement for other reasons is not support for this proposal.
